Source VMDK, then golden copy on Windows, then working copy, then converted qcow2 on conversion-host-01.

Why it matters: It answers the question: where is the migration disk right now?

What we have actually proven

PROVEN: 1A-1GKUBEVIRT: DESIGNED ONLY

Source, disk copy, conversion, KVM boot and nginx are proven. KubeVirt is not.

Why it matters: Only proven items count as evidence.

Every green tick was observed in a PASS stage record from 1A to 1G. KubeVirt is the only area that is design only.

  • UEFI boot proven with Secure Boot off; Secure Boot on is NOT TESTED.
  • Network fix proven on an isolated test network; DNS not proven.
  • libvirt proven only with the learning image.

08

Two conversion paths (Stage 1G)

PROVEN: BOTH BOOTED

qemu-img changes the box. virt-v2v changes the box and what is inside.

Why it matters: Stage 1H chose the virt-v2v output as the base for the future import image.

Both converted the same protected working copy to qcow2, and both booted under QEMU/KVM with UEFI and virtio. Neither fixed the network; one netplan change did.

  • qemu-img: 5 s, guest bytes identical.
  • virt-v2v: 136 s; VMware Tools removed, initramfs rebuilt.
  • virt-v2v -o kubevirt: NOT TESTED.
09

How the network changes

1G FIX: PROVENKUBEVIRT NETWORK: DESIGNED

The NIC name changes, so the old netplan breaks. Matching by driver fixes it.

Why it matters: A VM that boots without a network is still a failed migration.

VMXNET3 becomes virtio-net, and ens192 becomes enp0s3. Netplan still looked for ens192, so the guest had no network until one netplan change. The KubeVirt design uses the same fix with DHCP behind masquerade.

  • 192.168.50.31 is not preserved (ADR 008).
  • Continuity = the same nginx page hash through a NodePort Service.
  • DNS: not proven.
10

How the disk storage changes

VMDK TO QCOW2: PROVENRAW ON PVC: DESIGNED

qcow2 in transit, raw on a Block PVC at rest. The PVC part is design only.

Why it matters: Storage choices decide what the VM can do later.

The VMDK was copied cold and converted to qcow2 in the lab. The design uploads a qcow2 through CDI into a 40 GiB gp3 Block PVC, stored raw. No PVC or DataVolume exists.

  • The DataVolume is standalone: deleting the VM keeps the disk.
  • ReadWriteOnce: not live-migratable, accepted for a cold migration.
  • Route for moving the qcow2 to AWS: DEFERRED to 1I.
11

The Stage 1H target (ADRs 007 to 010)

DESIGNEDNOT DEPLOYED

Every layer of the target is chosen on paper. None of it exists.

Why it matters: The build stage will not have to guess: the target is fully specified.

One EC2 m8i.xlarge node in ap-south-1 with nested virtualization, CentOS Stream 9, Kubernetes 1.36 by kubeadm, KubeVirt v1.9.0 and CDI v1.66.1. The migrated guest would run in a virt-launcher Pod on QEMU/KVM.

  • CDI v1.66.1 is a candidate until the runtime gate passes.
  • About USD 0.24 per hour while running; destroyed after each session.
  • EKS deferred, not rejected (ADR 007).
