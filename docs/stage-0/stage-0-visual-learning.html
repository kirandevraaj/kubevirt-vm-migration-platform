01

Big picture: one VM, two possible futures

STAGE 0 DESIGNCONCEPT

Start with one Linux VM running nginx on ESXi. The question is how to move it to Kubernetes. The migration path moves the whole VM onto KubeVirt, where it is still a VM, now managed by Kubernetes. The modernization path repackages only the application as containers, so the VM disappears.

Why this matters: Most later decisions depend on which of the two paths you are on.

Remember this: MIGRATION = the VM remains a VM. MODERNIZATION = the VM dependency is removed.

Technical details

Stage 0 overview and the first demonstration, which is designed but not built. Read: architecture.md, migration-architecture.md, modernization-model.md.

02

VMware to KubeVirt: same guest, different stack

DOCUMENTEDTARGET: STAGE 0 DESIGN

ROUGH ANALOGY VMware lens: ESXi + hostd become Kubernetes + KubeVirt. The VMX process becomes QEMU inside a Pod.

On the left, ESXi runs a VM with VMware virtual hardware. On the right, Kubernetes and KubeVirt manage a VirtualMachine object, and a virt-launcher Pod runs QEMU on KVM. Both stacks end with the same Ubuntu and nginx.

Why this matters: It shows what a migration must replace and what it must leave alone.

Remember this: Same guest OS. Different management and virtualization stack.

Technical details

How the two stacks are layered, and what KubeVirt adds to Kubernetes. Read: virtualization-fundamentals.md, kubevirt-architecture.md.

03

Three compute worlds

CONCEPT

World A is a traditional VM on ESXi. World B is the same VM run by KubeVirt. World C is the application as a container, with no guest OS. Migration moves A to B; modernization moves A or B to C.

Why this matters: Without this split, "moving to Kubernetes" can mean two different projects at once.

Remember this: Migration = A → B. Modernization = A/B → C.

Technical details

The comparison table and the worked nginx example. Read: modernization-model.md.

LEVEL 2

Understand the technologies

KVM, QEMU, VirtIO and KubeVirt: what each one does.
04

The virtualization stack

DOCUMENTED

ROUGH ANALOGY VMware lens: ESXi VMkernel ≈ Linux + KVM. VMX process ≈ QEMU. hostd / vCenter ≈ Kubernetes API + KubeVirt.

Every VM platform has the same layers: hardware, hypervisor, virtual hardware, guest OS, application and a manager. VMware, plain KVM and KubeVirt-managed KVM differ only in the hypervisor, virtual hardware and manager rows.

Why this matters: It tells you which layer each migration problem lives in.

Remember this: Migration changes the lower machinery and the manager, not the guest.

Technical details

Hypervisor types, and how ESXi and KVM compare layer by layer. Read: virtualization-fundamentals.md.

05

KVM, QEMU and libvirt: three jobs, one VM

DOCUMENTEDMOST IMPORTANT

ROUGH ANALOGY VMware lens: VMkernel's VMM ≈ KVM. VMX process ≈ QEMU. hostd ≈ libvirt. ESXi does all three as one product.

KVM is a Linux kernel module that runs guest code on the real CPU using VT-x or AMD-V. QEMU is one user-space process per VM that builds the machine: firmware, chipset and devices. libvirt describes the VM as domain XML and starts QEMU.

Why this matters: Every KubeVirt VM is this exact stack inside a Pod. Debugging starts with knowing which layer failed.

Remember this: KVM runs the VM; QEMU provides the machine; libvirt manages it.

Technical details

KVM, QEMU and libvirt in detail, and how KubeVirt uses them. Read: virtualization-fundamentals.md, kubevirt-architecture.md.

06

VirtIO: the hardware changes under the guest

DOCUMENTEDRISK: DRIVERS

ROUGH ANALOGY VMware lens: PVSCSI → virtio-blk / virtio-scsi. VMXNET3 → virtio-net.

VMware guests use PVSCSI disks and VMXNET3 NICs. Under KVM the guest sees virtio-blk/scsi and virtio-net. The drivers must be in the initramfs for the guest to boot. qemu-img changes only the disk format; virt-v2v also adapts the guest.

Why this matters: New hardware under an unchanged guest is the usual reason a converted VM fails to boot or has no network.

Remember this: The disk bytes move; the hardware under them changes.

Technical details

Device models, and where guest conversion fits in the flow. Read: virtualization-fundamentals.md, migration-architecture.md.

07

What is KubeVirt?

DOCUMENTED

KubeVirt is a Kubernetes add-on. It adds new object types such as VirtualMachine, controllers that act on them, and a node agent. A VM becomes something you kubectl apply, protect with RBAC and schedule like a Pod. It does not replace KVM; it drives QEMU and KVM from inside Pods.

Why this matters: Everything else in Stage 0 builds on this one idea.

Remember this: KubeVirt makes VMs manageable through Kubernetes.

Technical details

KubeVirt components, objects and what the nodes need. Read: kubevirt-architecture.md.

08

KubeVirt component map

DOCUMENTED

virt-operator installs and upgrades KubeVirt. virt-api provides admission webhooks and subresources such as start, stop and console. virt-controller turns VMs into VMIs and virt-launcher Pods. virt-handler runs on every VM node and tells virt-launcher to define and start the libvirt domain.

Why this matters: When a VM will not start, the failing component tells you where to look.

Remember this: Cluster brain: virt-controller. Node hands: virt-handler.

Technical details

The component table and the full lifecycle of starting a VM. Read: kubevirt-architecture.md.

09

VM vs VMI

CONCEPTDOCUMENTED

The VirtualMachine is the persistent definition: it exists while the VM is stopped and holds runStrategy. The VirtualMachineInstance is one running instance. virt-controller creates it when the VM should run and deletes it when it stops.

Why this matters: Lifecycle questions, such as what survives a stop or what restarts a crash, depend on this split.

Remember this: VM = specification. VMI = running instance.

Technical details

VM, VMI and runStrategy. Read: kubevirt-architecture.md.

LEVEL 3

Understand Kubernetes control

CRDs, controllers, reconciliation and status.
10

CRD → controller → VM

CONCEPTKEY IDEA

A CRD teaches the API server a new object type, such as VirtualMachine. Creating an object of that type only stores data. A controller watches those objects, compares desired with actual state, and creates or updates resources until they match. Status flows back to the object.

Why this matters: The planned migration platform is exactly this pattern: a new CRD plus our own controller.

Remember this: CRD = defines a new API type. Controller = implements the behavior.

Technical details

CRDs, controllers, informers and work queues. Read: crd-controller-fundamentals.md.

11

The reconciliation loop

CONCEPTDOCUMENTED EXAMPLE

A controller does not run a script once. It observes, compares, takes one idempotent step, then observes again. Example: with runStrategy: Always, if the VM crashes, virt-controller creates a new VMI. That is documented KubeVirt behavior; Stage 0 did not test it.

Why this matters: Idempotent, restart-safe steps are what make a long migration survivable.

Remember this: Controller = state convergence.

Technical details

The reconcile loop, idempotency and requeueing. Read: crd-controller-fundamentals.md.

12

Spec, status and conditions

CONCEPTSTAGE 0 DESIGN

spec is what you want; only you write it. status is what actually happened; only the controller writes it. The designed migration CR reports independent conditions such as SourceDiscovered, DiskImported and Ready, each with a reason, a message and observedGeneration.

Why this matters: You debug a controller by reading status, so status must be honest and specific.

Remember this: The controller reports what it knows.

Technical details

status.phase, conditions and observedGeneration, as designed. Read: crd-controller-fundamentals.md, migration-architecture.md.

13

The KubeVirt resource chain: who owns this?

DOCUMENTEDROUGH ANALOGY

ROUGH ANALOGY VMware lens: VM in inventory ≈ VirtualMachine. VMX process ≈ QEMU in virt-launcher. VMkernel's VMM ≈ KVM.

Seven layers, each with a different owner. You (or the migration controller) own the VirtualMachine. virt-controller owns the VMI and creates the virt-launcher Pod. virt-handler has the libvirt domain defined. libvirt runs QEMU, the node kernel provides KVM, and the application team owns the guest.

Why this matters: "Who owns this layer?" is the fastest way to find the right logs.

Remember this: VM → VMI → virt-launcher Pod → libvirt → QEMU → KVM → guest.

Technical details

The start-up sequence, step by step. Read: kubevirt-architecture.md.

LEVEL 4

Understand migration mechanics

Storage, CDI, the source model, the flow, the state machine and networking.
15

Storage object stack

DOCUMENTEDAWS: STAGE 0 DESIGN

ROUGH ANALOGY VMware lens: VMDK ≈ PVC. Datastore + storage policy ≈ StorageClass. Datastore upload ≈ DataVolume import.

The guest sees a virtio disk. It comes from a PVC, which a DataVolume filled. A StorageClass is a policy that tells a CSI driver to create one real volume per claim, for example an EBS gp3 volume on AWS.

Why this matters: Storage settings such as access mode and zone decide what the VM can and cannot do later.

Remember this: One disk = one PVC. A StorageClass is a policy, not a pool you browse.

Technical details

PVCs, StorageClasses, CSI and the planned AWS storage. Read: cdi-storage-model.md.

14

CDI data path

DOCUMENTEDSTAGE 0 DESIGN

CDI takes a disk image (qcow2, VMDK or raw), imports or receives it, converts it to raw and writes it into a PVC, reporting progress on a DataVolume. CDI ends when the DataVolume is Succeeded. KubeVirt begins when a VM references the PVC.

Why this matters: A clear boundary tells you which system to debug when a migrated VM has a disk problem.

Remember this: CDI imports / prepares disk into Kubernetes storage. CDI does not run VMs.

Technical details

CDI sources, DataVolume phases and scratch space. Read: cdi-storage-model.md.

16

The VMware source model

DOCUMENTED

ROUGH ANALOGY VMware lens: These are the objects you know from the Host Client: inventory, .vmx, .nvram, VMDK, vNIC, port group.

A VMware VM is three kinds of information. Metadata (inventory, .vmx, firmware, NICs) is small and is translated into a VM spec. Disk data (the VMDK) is large and is copied and converted after power-off. Runtime state (power, IP lease, VMware Tools) is only observed.

Why this matters: Each kind is handled at a different time, by a different step.

Remember this: Metadata is translated, disk data is copied, runtime state is only observed.

Technical details

The source model and what a free ESXi host exposes. Read: vmware-source-model.md.

17

Migration architecture

STAGE 0 DESIGNCONTROLLER: NOT BUILT

The designed cold-migration road has three rows. On the source side the VM is discovered, assessed and powered off, and its disk is copied. The disk is then converted and staged. On the Kubernetes target, CDI imports it and a KubeVirt VM is created and validated. A future controller sits on top.

Why this matters: This is the whole project on one page. Each box later becomes a controller phase.

Remember this: Stage 0 designed the whole road; nothing on it was built in Stage 0.

Technical details

The flow table, cold vs warm, MTV as reference and the CRD sketch. Read: migration-architecture.md, ADR 003, ADR 005.

18

Migration state machine

STAGE 0 DESIGNKEY IDEA

The designed status.phase goes from Pending through Discovering, Validated, Preparing, Converting, Importing, CreatingVM, Starting and Validating to Completed. Transient errors go to Retryable and resume the same phase. A human decision goes to ManualInterventionRequired. Permanent errors go to Failed.

Why this matters: Checkpoints make a half-finished migration resumable instead of a mystery.

Remember this: State machine = reconciliation checkpoints.

Technical details

Per-phase desired and observed state, transition types and idempotency rules. Read: migration-state-machine.md.

19

Networking model

DOCUMENTEDSTAGE 0 PLAN: MASQUERADEMULTUS: DEFERRED

ROUGH ANALOGY VMware lens: vNIC ≈ virtio NIC in interfaces[]. Port group ≈ networks[] entry. vSwitch ≈ CNI dataplane + in-pod plumbing.

In KubeVirt, networks[] says where a NIC connects (the pod network or a Multus network), and interfaces[] says how (the binding). The Stage 0 plan is one NIC on the pod network with masquerade, reached through a Service. Bridge and Multus are optional and deferred.

Why this matters: Networking changes more in a migration than anything else, including the VM's IP address.

Remember this: networks[] = where. interfaces[] = how.

Technical details

Bindings, Multus, NADs and the ESXi comparison. Read: networking-model.md.

20

Network mapping

STAGE 0 DESIGNRISK: GUEST CONFIG

ROUGH ANALOGY VMware lens: Port group + VLAN + vNIC settings are the source of the mapping.

Every NIC needs five answers: destination network, binding, IP addressing, MAC address and guest OS configuration. With masquerade, the guest must use DHCP, so a static VMware IP will not work as-is. The interface name can change (ens192 to enp1s0), which can break netplan.

Why this matters: A VM that boots but has no network is still a failed migration.

Remember this: Network migration is a mapping problem, not simply a NIC swap.

Technical details

The mapping rules and the demo plan. Read: networking-model.md.

21

Migration vs modernization

CONCEPTEXAMPLE: DESIGN

Migration moves the whole machine and ends as a KubeVirt VirtualMachine; the guest OS is kept and still patched like a VM. Modernization moves only the application into a container image run by a Deployment, and the guest OS goes away.

Why this matters: Treating a migrated VM as modernized hides the guest OS you still have to operate.

Remember this: Migration keeps the VM; modernization removes it.

Technical details

The comparison table and the nginx worked example. Read: modernization-model.md.

Feasibility decision map

VALIDATEDDOCUMENTEDUNVALIDATEDBLOCKEDDEFERRED

Stage 0 sorted every finding into five categories. Validated means we saw it work. Documented means official docs say so, but we did not run it. Unvalidated means unknown. Blocked means impossible in the current lab mode. Deferred means intentionally not decided yet.

Why this matters: It stops paper decisions from being mistaken for proven facts.

Remember this: Architecture decisions are different from proven runtime facts.

23

Stage 0 decisions: ADR 001 to 005

DECIDED (ACCEPTED)

Five accepted decisions answer the big questions. 001: the source is a local nested ESXi. 002: the target is AWS, Terraform-only and disposable. 003: cold before warm. 004: upstream KubeVirt + CDI. 005: a custom controller owns the workflow, with scripts only as building blocks.

Why this matters: ADRs record why, so later stages do not quietly re-decide.

Remember this: Where from, where to, how, onto what, who orchestrates.

Technical details

Read each decision record. Read: ADR 001, ADR 002, ADR 003, ADR 004, ADR 005, ADR index.

Stage 0 interview visuals

From interview-notes.md. Click a question.
Q1 How would you migrate a VMware VM to Kubernetes?

Rehost it as a KubeVirt VM: discover and assess, power off (cold), convert the disk and guest drivers, import the disk into a PVC with CDI, create a VirtualMachine with storage and network mappings, boot it and validate the app.

See diagram 17 →

Q2 What is KubeVirt?

A Kubernetes add-on that runs and manages VMs as Kubernetes objects, next to containers, using the Kubernetes API, scheduler, networking and storage.

See diagram 07 →

Q3 What is the difference between a VM and a VMI?

The VirtualMachine is the persistent definition and desired run state; the VMI is one running instance of it. Like a StatefulSet with one replica versus its Pod.

See diagram 09 →

Q4 How does KubeVirt run a VM?

VirtualMachine, then virt-controller creates a VMI and a virt-launcher Pod, the scheduler places it, virt-handler has libvirt start the domain, and QEMU runs the VM on /dev/kvm.

See diagram 13 →

Q5 Where does QEMU run?

In user space, inside the compute container of the VM's virt-launcher Pod, on the node where that Pod was scheduled. One QEMU process per VM.

See diagram 13 →

Q6 What is KVM?

A Linux kernel module that turns Linux into a hypervisor using VT-x / AMD-V. It exposes /dev/kvm, which QEMU uses to create VMs and run vCPUs.

See diagram 05 →

Q7 What does CDI do?

It fills PVCs with VM disk data: import, upload, clone or blank. It converts images to raw and reports progress on a DataVolume. It knows nothing about CPUs or NICs.

See diagram 14 →

Q8 How would you design a migration CRD?

One namespaced CR per VM migration: a declarative spec (source, destination, strategy, storage and network mapping, validation) and a controller-owned status (phase, conditions, progress, inventory, errors).

See diagram 12 →

Q9 What happens when migration fails halfway?

The CR keeps the phase and records the error. Transient errors retry in the same phase; permanent ones go to Failed or ManualInterventionRequired. The source disk is intact, so the source can be powered back on.

See diagram 18 →

Q10 What is the difference between VM migration and application modernization?

Migration moves the whole VM, guest OS included, without changing the app. Modernization repackages the app, for example as a container in a Deployment, which removes the VM and guest OS.

See diagram 21 →
